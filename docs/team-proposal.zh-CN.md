## 1. 比赛与共同目标

Perpetual Alpha 是 ICAIF 2026 的实时算法交易比赛。我们需要自己运行程序，通过 API 在 Hyperliquid 测试网的专用 `par` 市场获取行情、下单、撤单和管理仓位，使用主办方提供的测试资金。

我们已经完成组队、报名、创建比赛钱包和提交公开地址。主办方审核、资金到账、Discord 队伍频道及账户授权进度需要再确认。

建议共同目标是：**先完成可靠的参赛系统，再通过实验提高策略表现，最后形成完整的代码、研究记录和技术报告。**

比赛综合评价收益、风险和算法质量；详细规则还要求至少在 10 个不同日期交易，并达到最低累计名义成交额。具体成交额阈值及统计口径需要确认。[官方规则](https://perpetual-alpha26.github.io/about)

主要时间节点：

## 2. 建议分工

考虑到你正在做 AI Infra，我想先和你讨论是否由你侧重数据与系统工程，我侧重项目推进、策略实验和结果整理。交易与量化部分我们一起补基础、一起检查，实际任务量根据各自能够承诺的时间确定。

| 工作 | 我可以主要推进 | 想和你讨论的职责 | 共同决定或检查 |
|---|---|---|---|
| 项目管理 | 规则、日程、主办方消息、任务与记录 | 技术工作量和依赖评估 | 每周目标、任务优先级 |
| 数据 | 数据需求、样例检查、研究分析 | 采集、存储、时间对齐、质量检查 | 数据格式与可靠性 |
| 策略研究 | 假设整理、基准实验、结果分析 | 协助实现、检查计算与验证流程 | 策略选择、实验结论 |
| 交易与风控 | 场景整理、测试、交易结果核对 | API、订单状态、账户恢复、风控实现 | 风险范围、上线条件 |
| 部署与运行 | 每日摘要、异常记录、运行检查 | 部署、监控、进程恢复 | 应急操作与值守安排 |
| 报告 | 实验记录、报告结构与结果整理 | 架构说明、工程验证材料 | 最终报告与代码说明 |

每项任务约定负责人、交付时间、完成标准和交接说明；两个人都需要会查看仓位、停止交易和检查剩余风险。

如果只能零散投入，就拆成独立任务，例如数据采集、订单逻辑检查或部署演练；如果能稳定投入，再按完整工作线分工。时间不足时减少研究分支和功能，保留必要的交易与风控验证。

## 3. 技术架构建议

整体流程：

**行情与账户数据 → 清洗和特征 → 策略目标仓位 → 风控 → 订单执行 → 成交、账户核对与记录。**

技术上分为三个部分：

- **数据**：REST 用于历史补数和账户查询，WebSocket 用于实时变化；保存价格、报价、成交量、参考价、资金费，以及自身订单、成交和账户净值。统一时间，并记录事件时间和接收时间。
- **研究**：回测、实时观察和实际交易尽量共用特征与信号逻辑。策略输出目标仓位，执行模块负责根据真实仓位和未完成订单决定怎样操作。
- **运行**：处理拒单、部分成交、超时、断线和重启；行情或账户异常时暂停增加风险。日志需要能够解释每笔交易为何发生及其实际结果。

初步工具方向为 Python、pandas/NumPy、官方 SDK、SQLite 和数据文件；模型研究可用 scikit-learn，正式运行考虑 Linux 服务器。先采用一个统一交易进程，具体配置实施时再定。

账户查询使用队伍公开地址，交易程序使用授权 API 钱包；主钱包保留管理权限。账户初始化与测试交易在主办方资金到账后进行。[参与指南](https://perpetual-alpha26.github.io/docs/)

### 数据来源与模型训练

建议采用“比赛实时数据＋外部长历史＋自行积累的比赛历史”组合：

- **实时交易与比赛验证**：从 Hyperliquid 测试网的 `par` 接口接收行情与账户事件，并持续保存；市场名称使用 `par:BTC`、`par:ETH`。
- **近期比赛历史**：通过历史接口补数。K 线只保留最近 5,000 根，不能依靠分页获取无限长历史。
- **长期训练数据**：从 Binance 官方公开数据站获取 BTCUSDT／ETHUSDT 的 USD-M Futures 历史，第一轮建议最近 6–12 个月的 1 分钟 K 线，再汇总到研究周期。
- **主办方数据**：检查 Discord／邮件是否发布。10 月 7 日公开 FAQ 仍未提供下载链接；发布后按实际内容补充。

外部数据支持初步训练，比赛数据验证信号、成本和执行。盘口、参考价或领先关系模型需要额外同步数据，普通 K 线不够；训练与运行特征也要来自一致的定义和数据源。

想和你讨论由你侧重比赛采集与存储，我推进官方来源确认、历史数据分析和基准实验，我们共同检查数据质量与特征一致性。完整来源、接口、限制和交付要求放在[《数据获取与模型训练开发规划》](data-development.zh-CN.md)。

## 4. 策略路线与探索范围

建议第一版只交易 BTC，条件允许时同时采集 ETH 数据。先建立简单趋势基准，再判断改进是否有价值。所有方向目前都是研究假设，不预设盈利能力。

我也把关于利率、美元、黄金、原油和股指的宏观想法记在[《研究想法与假设记录》](research-ideas.zh-CN.md)。先保存原始判断和待验证问题，后续一起选一条、确定数据与影响周期，再检查能否用来辅助信号或风险控制。

| 路线 | 研究问题／方法 | 优先级 |
|---|---|---|
| 趋势／动量 | 用均线、多周期收益或突破判断趋势延续 | 第一版基准 |
| 波动与成本控制 | 波动大时缩仓、价差大时暂缓交易，减少无效换仓 | 基准后的首个改进 |
| 参考价与外部信息 | 比赛盘口与参考价、外部市场的偏离或滞后是否有预测信息 | 首选探索分支 |
| 均值回归 | 短期偏离是否回归，如何区分偏离与新趋势 | 备选策略 |
| 跨资产 | BTC 是否能提供 ETH 的额外信息，关系是否稳定 | 系统稳定后考虑 |
| 订单簿信号 | 买卖深度和成交方向能否改善入场判断 | 先作为辅助特征 |
| ML 过滤器 | 用逻辑回归或树模型判断已有信号是否值得执行 | 数据和基准合格后 |
| 做市 | 挂双边报价能否覆盖成交不利与库存风险 | 暂不作为主线 |
| 深度学习／强化学习 | 更复杂的模型或决策方法是否有额外价值 | 保留为后续方向 |

建议组合为：

**主线：趋势基准 → 波动仓位控制 → 成本过滤。**  
**探索：参考价格与比赛盘口的关系。**  
**可选升级：简单 ML 过滤器。**

参考价格与可成交价格不同，偏离本身不等于套利机会。先观察关系，再检查延迟、费用、价差和滑点；有可靠证据后，优先把信息用于过滤主策略的入场。[价格机制](https://perpetual-alpha26.github.io/docs/#asset-references-and-pricing)

第二周同时推进的额外探索分支建议最多一个，其他路线保留在候选池。周期、门槛、模型和仓位参数通过实验确定。

## 5. 如何验证与选择版本

按 **历史回测 → 未参与调参的数据验证 → 实时观察但不下单 → 小仓位测试网运行** 推进。

- 按时间切分数据，避免未来信息进入训练；只用完整结束且当时已收到的数据形成信号。
- 回测包含手续费、价差、滑点和资金费，不假设所有订单都能按理想价格成交。
- 一次改变一个主要因素，固定对照口径；保留失败实验，检查参数和成本变化后的表现。
- 比较净收益、每日收益波动、最大回撤、费用、交易次数、成交额和风险敞口，同时跟踪参赛资格。
- 选择版本时结合成本后结果、风险、稳定性和解释性，不能只看预测准确率或短期收益。

上线前共同检查断线、行情过期、拒单、部分成交、超时、重启和停止交易等情形。停止或平仓失败时必须能够看到剩余订单与仓位。
