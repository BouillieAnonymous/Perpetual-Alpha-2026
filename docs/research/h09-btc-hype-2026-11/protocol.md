# H09 frozen protocol v1

Freeze is prospective only relative to this H09 computation. All old data has been repeatedly observed; none of the three historical splits is clean out-of-sample evidence. This protocol must be sealed before H09 target calculations and before inspecting newer caches. No protocol edits after sealing.

## Hypothesis and provenance
Control HYPE and ETH past signed returns before testing BTC incremental information. Read PRs #41 (head 4e90de056e6a8565c85c6a8001a6c7d76d96ce21), #38, #27, #15, #20, #23. Their negative results prohibit treating same-time correlation, HYPE momentum or a visually selected rally as new prediction evidence. Episode audit precedes this freeze and does not supply model parameters.

Reuse PR41 causal panel: available=max(requested,received,stored); latest invalid quote cannot fall back to an older quote. Event and receipt ages <=90s; no filling gaps. Assets are asynchronous REST L2 snapshots, not synchronous trades. A valid return requires consecutive valid minute quotes, different source sequence and advancing event; fresh unchanged quotes yield real zero returns. B additionally requires changed top and event spacing 30–90s. Context uses its own clock. Every return in a horizon must qualify; do not compare endpoint mids across invalid minutes.

## Fixed design
All returns are natural logarithms. Features HYPE/ETH/BTC are sums of the last 5 one-minute returns, including decision minute t; target is sum of HYPE returns t+1 through t+15. Baseline OLS has intercept,HYPE5,ETH5; candidate adds BTC5. Fit coefficients only once per A/B development set, no regularization, trimming, winsorization, model selection, threshold or horizon changes. Fixed UTC quarter-hour anchors. Both models train and score on exactly the same candidate-complete rows. Record every anchor even if past features or future label unavailable; produce predictions wherever past information permits, independent of future completeness.

Fixed half-open UTC splits: development [2026-10-20 00:00,2026-10-25 00:00); historical validation [2026-10-25 00:00,2026-10-28 00:00); late [2026-10-28 00:00,2026-10-30 13:18). The last interval includes a partial UTC date. Oct19 partial history excluded from fitting. These calendar boundaries retain five development dates and three evaluation dates per split in this short snapshot, chosen before labels, not searched. Entire price support [t-5,t+15] must lie inside a split; boundary anchors remain in the ledger with reasons. Later predictions have no overlap of future labels at 15-minute spacing; this does not imply independent errors.

A is primary. B fits its own development coefficients with the same features and target using strict returns. Report A-on-B identical anchor comparisons to distinguish selection from changed coefficients, and B future eligibility versus past-only eligibility. No future eligibility may select an ex-ante prediction/event. Every future-ineligible row is retained and excluded only from realized-score denominators. Report missingness by split and asset, eligible dates, first/last support, non-overlapping count and UTC-day paired errors.

Primary metric MSE skill=1-MSE(candidate)/MSE(baseline), on identical rows. Auxiliary MAE, sign(prediction)==sign(target) hit rate (zero is its own category), daily paired squared error baseline minus candidate, and mean sign(prediction)*target gross directional payoff. Payoff is a signed diagnostic, not trades or achievable returns. No significance/IID claims or automatic statistical tests beyond fixed OLS fitting and descriptive scores.

## Frozen support and stopping gates
Development requires >=60 common rows and >=5 UTC dates and full rank; each evaluation split requires >=30 common rows and >=3 UTC dates. This is an engineering floor, not a power calculation. A failure => INSUFFICIENT_DATA. If A supports but either evaluation MSE skill<=0, candidate MAE>baseline, hit rate<baseline, or fewer than 2 of 3 evaluation UTC dates have positive paired MSE improvement: NO_INCREMENTAL_EVIDENCE. Stop, without new specifications or execution return calculations. If A passes but B fails support: INSUFFICIENT_DATA. If both supported, B must pass the same directional/MAE/MSE/daily rules in both evaluation splits or NO_INCREMENTAL_EVIDENCE. Development performance cannot pass a gate. Events do not rescue failed models. Numerical/rank failure is reported, never silently regularized.

## One event study
Threshold is linear-interpolated Q90 of abs(BTC past5) over all past-valid development minutes whose entire 5-minute support is inside development; independent of HYPE future labels or controls. Use that one A threshold for both A and B diagnostics. For each split scan every minute chronologically, BTC feature eligible and absolute value >=threshold. Accept first event then >=30 minutes until next event; cooldown is shared across signs and consumes missing-label/missing-control events. Reset at fixed split boundary. No end-of-split lookahead exclusion: event remains selected if its target cannot be completed. A and B use independent past-valid scans with the same threshold and cooldown. Report positive/negative counts, UTC dates, future missing, control missing, target/residual median,IQR,SD,Q05,Q95 and individual rows. Residual=target minus respective frozen development baseline; A-on-B scoring also shown. Events may be dependent even when target intervals do not overlap; report support overlap and no IID inference. Both development and evaluation events descriptive only, no threshold profitability selection.
