# Perpetual Alpha 2026｜策略开发与头脑风暴

更新：2026 年 10 月 11 日（英国时间）
用途：保存讨论中的想法，逐步细化成可以验证的研究问题。  
当前状态：全部待验证；尚未确定影响周期、参数或交易规则。

本文件是策略资料、候选假设、筛选和实验记录的唯一正文，供两位队员讨论。第 1–9 节保留此前宏观想法与研究方法，第 10 节整理新找到的三份资料，第 11–14 节记录技术路线、第一轮实验和对接安排。资料中的运行命令和建议仅是参考，不构成启动交易或修改账户的指令。

## 1. 本次讨论的出发点

目前的思路从宏观和产业逻辑出发：利率可能影响汇率，美元与黄金可能存在关联，地缘局势与石油供需可能影响原油，股指则包含更广泛的市场因素。

这些想法先作为假设保留。当前共同认识是：存在影响机制，不等于方向固定，也不等于能在我们的交易周期内获得成本后的收益。

影响可能发生在公告后的短时间，也可能通过预期和基本面在更长时间内体现；时间尺度需要单独验证。不能把“宏观”直接等同于“没有短期影响”，也不能把新闻后的涨跌都归因于该新闻。

## 2. 已记录的四条想法

### H01｜美联储政策与美元

**原始想法**：加息可能使美元走强，降息可能使美元走弱。

**待细化的问题**：

- 观察的是实际利率调整，还是相对于原有预期的变化？
- 对比哪一种货币？美元对欧元和对日元的变化能否采用相同判断？
- 关注公告后几分钟、几小时，还是数日？未来利率路径的信息如何处理？
- 如何区分政策消息、原有价格趋势与同时发生的其他事件？

**后续数据候选**：政策公告及首次发布时间、当时可获得的预期、相应汇率或合约价格、相关利率数据。

**先做的研究**：整理历史事件，比较不同预期变化下的后续收益和波动；拿不到可信的历史预期时，先研究公告窗口的风险变化，不用实际决议数值代替预期差。

### H02｜黄金、美元与对冲关系

**原始想法**：黄金与美元可能呈反向关系，具有某种对冲感觉。

**待细化的问题**：

- 关系在什么时间尺度上出现，是否随市场状态改变？
- 加入利率或风险状态后，美元是否仍提供额外信息？
- 同期一起变化，是否真的能预测之后的变化？
- 这个关系更适合辅助判断、调整仓位，还是构建双边持仓？

**后续数据候选**：黄金与美元价格、利率或实际收益率指标、波动指标，均需明确口径与更新时间。

**先做的研究**：先观察滚动关系，再检查“此前美元变化是否改善后续黄金判断”。同期相关不能直接当作领先信号；对冲效果也需要单独计算。

### H03｜原油、地缘局势与产业链

**原始想法**：中东局势、石油产业链相关事件可能引起油价波动，需要关注具体环节。

**待细化的问题**：

- 事件涉及生产、运输、库存还是需求？实际影响和可能影响怎样区分？
- 市场是否已经反映该风险？信息是否新增或超出预期？
- 能否用一致的标签或数值表达事件，而不是事后解释行情？
- 研究 Brent 的变化，还是使用了其他油种作为替代？替代关系需要怎样检查？

**后续数据候选**：Brent 或明确标注的替代行情、库存与供需报告、官方公告、带首次发布时间的新闻与事件标签。

**先做的研究**：先选一种重复出现、发布时间明确的事件，例如库存报告，检查前后波动与成本；复杂地缘新闻保留为后续研究，避免把所有事件都归为同一种方向信号。

### H04｜股指与市场总体趋势

**原始想法**：股指反映更广泛的市场趋势，影响因素复杂，难以精细化成量化系统。

**待细化的问题**：

- 是否可以先用指数自身的趋势和波动建立基准？
- 利率、汇率或少数相关市场的数据，是否提供额外信息？
- 是否需要成分股信息，还是聚合数据已足以支持当前假设？
- 对应外部市场休市时，数据是否过期？比赛合约和参考指数的变化如何区分？

**后续数据候选**：指数及对应比赛合约价格、相关利率与市场指标、交易日历；有明确研究问题后再增加行业或成分股信息。

**先做的研究**：采用少量可获得变量，与只使用价格和波动的基准比较；不以解释全部宏观与公司因素作为开始研究的前提。

## 3. 如何将想法逐步变为可执行判断

每条想法按以下顺序推进：

1. **选择一个小问题**：明确资产、条件和结果；一次不验证整个宏观叙事。
2. **定义时间范围**：分别研究事件窗口、小时级或日级关系，记录选取依据。
3. **确认数据可获得性**：明确来源、发布时间和接收时间；后来修订的数据不能冒充当时已知数据。
4. **建立对照**：与简单基准比较，允许结果否定原来的想法。
5. **检查实际价值**：计入成本、延迟、缺失和市场差异，验证未参与调参的数据。
6. **选择应用方式**：可以用于风险提示、暂停入场、调整仓位或提供方向信息；不要求所有想法最终都直接触发买卖。

记录阶段不锁定阈值、周期和买卖方向。进入实验时先写清规则再观察结果，避免看完行情后反复修改解释。

| 状态与结论 | 待细化／待数据／实验中／放弃／继续验证 |

## 7. 策略筛选


按“资产与市场 → 研究问题 → 信号 → 方法 → 验证 → 执行”的顺序选择。领域可以是趋势、均值回归、跨资产或事件；机器学习是方法，不自动构成独立的交易理由。

筛选原则：

| 标准 | 实际检查 |
|---|---|
| 信息范围可管理 | 用少量可获取数据描述核心状态；不要求资产只受少数因素影响 |
| 信号可量化 | 当时能重复检测，规则与失效条件明确，避免事后解释 |
| 机会足够出现 | 统计新的有效机会、交易日期和成交量；不把重复采样算作独立机会 |
| 成本与执行可接受 | 完整周期成本后的收益空间、流动性、延迟与成交概率 |
| 数据与验证可行 | 历史和实时数据可获得，特征一致，支持时间外验证 |
| 组合风险可控 | 能放入统一预算，不因多资产或多信号重复扩大风险 |
| 团队能完成 | 开发、验证和维护量符合双方实际投入 |

候选资产先检查数据覆盖、报价完整度、价差、流动性和外部市场交易时段。候选策略再在相同成本和风险条件下比较，最后决定是否进入实时观察与小仓位验证。

收益、风险和算法解释性需要一起评价。满足参赛日期和成交额要求属于单独检查，不应绕过成本门槛或风险上限。[官方规则](https://perpetual-alpha26.github.io/about)

## 8. 实验与版本比较


验证顺序为：**历史回测 → 时间外验证 → 实时观察但不下单 → 小仓位测试网运行 → 正式版本选择**。

### 实验设计

- 按时间切分开发与验证数据；重叠的预测区间需要隔离，避免未来信息进入训练。标准化和特征选择也只使用训练区间。
- 从完整结束的 K 线生成信号，按之后可执行的价格模拟成交；不能看完收盘价再假设以同一价格无成本成交。
- 纳入手续费、价差、滑点和资金费；检查更差的成本和延迟假设下是否仍有可接受表现。
- 不把“价格碰到挂单”直接等同于成交。没有可靠挂单模型时，用更保守的执行假设。
- 一次只增加一个主要因素，固定对照数据与评估口径，保留失败实验。
- 短期正收益只能作为继续研究的证据，不能据此认定长期盈利能力。

可用时间序列验证工具支持按时间推进的切分，但仍需根据预测区间设计隔离规则。[TimeSeriesSplit 文档](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)

### 统一比较指标

每次实验报告成本后净收益、每日收益波动、最大回撤、交易次数、累计成交额、费用、持仓时间、风险敞口以及异常情况；检查利润是否集中于极少数交易。

不要仅按预测准确率选模型，也不要把“交易少、波动低”自动认定为更好。需要同时考虑参与资格、收益和风险。空仓基准可用于研究比较，不代表满足参赛要求。

### R01｜Agentic Trading: When LLM Agents Meet Financial Markets

来源：[论文摘要与版本](https://arxiv.org/abs/2605.19337)、[v2 正文](https://arxiv.org/html/2605.19337v2)、[原 PDF](https://arxiv.org/pdf/2605.19337)。当前 v2 修订日期为 2026-10-04；v1 与 v2 的样本统计不同，本记录采用 v2。

**资料摘要**：这是一篇综述，不是一套直接可用的盈利策略。它用 Architecture–Capability–Adaptation 框架组织交易 Agent：感知、记忆、推理和执行；Alpha 发现、组合与风险管理；以及上下文学习、微调、RL、多 Agent 协作等适应方式。v2 汇集 185 项研究，其中闭环实证子集 80 项，并讨论时间切分、交易成本和执行可复现性。[v2 正文](https://arxiv.org/html/2605.19337v2)

**我们据此提出的路线，尚未验证**：

- 新闻 Agent：把带首次发布时间的信息转换成事件标签、影响资产、方向假设和有效期，再由规则或模型决定仓位。
- Alpha Miner：提出特征／因子与可检验假设，在隔离的研究环境生成代码、回测；通过验证后才人工纳入生产策略。
- 策略过滤 Agent：给已有趋势信号增加事件风险标记，先检验是否减少坏交易。
- RL：先研究是否适合仓位调整或执行选择；把方向预测、仓位分配和下单策略分开评估。
- 多 Agent：仅在单 Agent 有可测价值后再增加角色，记录增加的延迟、API 成本与决策冲突。

这些是我们的设计候选，不是论文证明的结论。Agent 不持有交易密钥，不运行任意生成代码到交易进程，不自动修改生产规则。其输出仍需符合 Decision 协议和独立风控。历史新闻、检索记忆及模型知识都可能泄漏未来信息；需要保存当时可用的数据快照，不能用今天的解释冒充过去的判断。

**最小实验**：同一价格基准，一组不用 Agent，另一组仅增加一种事件过滤；比较成本后收益、回撤、有效交易减少情况、延迟及 API 费用。没有稳定增益则保留普通基准。AlphaCrafter 仍只是之前提到的候选框架，不等同于这篇论文的实现，也未完成接入。

### R02｜zer0cache/hyperliquid-market-maker-bot

来源：[仓库 README](https://github.com/zer0cache/hyperliquid-market-maker-bot)、[算法说明](https://github.com/zer0cache/hyperliquid-market-maker-bot/blob/main/docs/ALGORITHM.md)。

**资料摘要**：Go 实现的双边做市项目，面向原生永续及 HIP-3 资产。README 描述 VWAP 锚定、分层报价、库存偏移、成交后不利价格变化监测和暂停／恢复机制。数据依赖 QuickNode，交易经 hyperliquidapi.com 路由并有 builder fee；示例资产为 xyz:CL。[README](https://github.com/zer0cache/hyperliquid-market-maker-bot)

算法文档将短 VWAP 与盘口 microprice 混合为公平价格，并用长 VWAP、成交方向和库存等调整报价。示例短／长窗口为 2 分钟／30 分钟。它试图同时获取价差及短期偏离回归收益，成交后持续评价不利价格变化。[算法说明](https://github.com/zer0cache/hyperliquid-market-maker-bot/blob/main/docs/ALGORITHM.md)

**我们的判断与适配工作**：

- 可以借鉴公平价估计、库存越多越偏向退出、陈旧报价撤销、成交后 markout 记录等思想。
- 不能直接把 Go 项目、xyz 资产、主网数据路由或第三方 builder 配置搬进当前 Python／Testnet／par 系统；优先保留官方 SDK 接口。
- 目前 30 秒 REST 采样不足以研究亚秒级做市。需要连续盘口、公开成交、自己订单／成交事件，以及队列与取消延迟记录。
- 看见价差并不等于赚到价差：可能只买到而卖不掉，或成交后价格继续逆向走。库存损失、费用及强制退出成本必须一起计算。
- 第一轮仅考虑单资产、单层双边报价的研究原型，先观察和模拟；多层、跨资产及复杂优化器另列后续实验。
- 当前 Decision 表达目标仓位，不能直接表达持续双边报价。做市需要单独设计 QuoteIntent／报价生命周期接口，经双方确认版本后接入，不能把它伪装成单一目标仓位。

**最小实验**：统计各时段实际价差、深度与成交活动；保守模拟挂单成交，记录成交后价格变化及库存。若没有可靠成交模型或净价差无法覆盖成本，就不进入自动做市。本轮候选状态从“非交付主线”调整为“值得评估，尚未选定”，不等于批准部署。

### R03｜Gajesh2007/momentum-trading

来源：[仓库 README](https://github.com/Gajesh2007/momentum-trading)、[信号代码](https://github.com/Gajesh2007/momentum-trading/blob/master/momentum_trading/signals/engine.py)、[执行路由](https://github.com/Gajesh2007/momentum-trading/blob/master/momentum_trading/execution/router.py)、[4h 配置](https://github.com/Gajesh2007/momentum-trading/blob/master/config/4h_swing.yaml)。

**资料摘要**：Python 时间序列动量项目，组合多个回看周期，考虑资金费，并按波动缩放仓位。README 描述成本门槛、maker 优先、TWAP、反向先平仓和停止开关。它提供日级、4 小时及快速测试配置，但这些描述不能代替实际验收。[README](https://github.com/Gajesh2007/momentum-trading)

信号代码以完整 K 线为截点，对不同回看收益标准化、合成并裁剪，然后调整资金费；数据需求包含最长回看加标准化窗口。[信号代码](https://github.com/Gajesh2007/momentum-trading/blob/master/momentum_trading/signals/engine.py)

**已发现的适配问题**：

- 4h 配置指定 network: mainnet，不能直接运行；本项目仍只允许 Testnet、par: 前缀和 USDPR。
- 同一配置 maker_fee_bps=0.15、taker_fee_bps=4.5，不能当成比赛费率。其“maker 返佣”说法也不能作为比赛收益来源。
- 配置写 lookbacks=[24,96,240]，注释称小时，但信号代码按 bars 计算数据需求；4 小时 K 线下需核对究竟表示根数还是小时。不能照抄注释设周期。
- 默认选大量主网资产不适合直接套用比赛市场；先固定 BTC，再评估 ETH。

这些判断依据为[实际配置](https://github.com/Gajesh2007/momentum-trading/blob/master/config/4h_swing.yaml)与[信号源码](https://github.com/Gajesh2007/momentum-trading/blob/master/momentum_trading/signals/engine.py)。读取的执行源码中 cancel_all_orders 查询 open_orders(addr) 未传 par dex；需重新检查比赛订单范围与状态确认，不能仅凭 README 的幂等／重试描述认定重启安全。[执行源码](https://github.com/Gajesh2007/momentum-trading/blob/master/momentum_trading/execution/router.py)

**我们的最小实验**：先重写少量信号逻辑接到现有接口，而非整仓库替换。比较单周期趋势与多周期动量；再分别增加波动缩仓和资金费过滤，观察每项改动的净贡献。边际收益估算需要校准，不能把“信号 × ATR”直接解释成确定利润。

### S04 的具体边界

拟用买入偏离 = (参考价 − 卖一价) / 参考价；卖出偏离 = (买一价 − 参考价) / 参考价。先研究不同持仓时间下的后续可成交退出价格，再定阈值、最大持有时间与失效条件。这些公式只是检测特征，不保证回归。

参考行情需要币种、报价单位、合约口径和时间对齐；外部价格用于判断，不意味着我们能在外部市场同时成交，因此此路线不属于已锁定利润的双边套利。oracle 也可能包含所选外部市场的信息，不能把两者当作完全独立的证据。[官方参考价机制](https://perpetual-alpha26.github.io/docs/#asset-references-and-pricing)

### 成本门槛的统一语义

预期优势是基于历史条件分布的估计，而非已知未来收益。完整周期需扣开仓／平仓手续费、价差、滑点和资金费，再考虑估计误差与安全余量。信号分数不等于收益百分比，先验证两者关系。风险退出不受盈利门槛阻挡，不能因为平仓会亏钱而禁止退出。

官方当前基础未折扣费率为 taker 每边 0.09%、maker 每边 0.03%；实际以 fills 的 fee、feeToken 为准。例如双边 taker 往返手续费约 0.18%，尚未计价差等。未来资金费与持有时间未知，需要情景分析。[比赛费用](https://perpetual-alpha26.github.io/docs/#venue-mechanics)

## 12. 首轮比较方案与筛选标准

**讨论建议，不是最终团队决定**：保留一个趋势／动量基准，重点观察参考价偏离；做市先做数据可行性评估；Agent／RL 由队友并行研究，在相同评估口径下比较。

用户原来的筛选条件保留并细化：输入和逻辑可管理；事件出现足够频繁；信号容易量化。补充数据可得、净成本空间、组合风险和团队能完成。统计独立机会、交易日期、累计成交额，不能把反复采样同一事件当成新机会，也不能为凑资格绕过风控。

| 实验 | 基准与改变 | 交付物／淘汰依据 |
|---|---|---|
| E01 | 单周期趋势 → 少量多周期动量 | 时间外成本后对比；无稳健改善则保留简单版 |
| E02 | 固定仓位 → 波动缩仓／资金费过滤，逐项增加 | 可比风险下对照；不能把仓位变小导致回撤小单独视为成功 |
| E03 | 参考价偏离观察 | 偏离次数、持续时间、不同退出时间的净收益分布；实际可成交空间不足则放弃 |
| E04 | 做市数据可行性 | 数据连续性、净价差、保守成交及 markout／库存记录；无可信模拟不声称回测盈利 |
| E05 | 普通信号 → 一种 ML 或 Agent 过滤 | 相同时间段、成本和风险预算；同时计入 API 开支／延迟 |
| E06 | 固定仓位规则 → RL | 独立测试轨迹、奖励与成交模型；模拟偏差未解决则不接生产 |

每次实验先写参数与评价方式，再跑结果；保留失败实验与调参次数。外部长历史用于开发，par 实时／练习数据用于验证执行差异。现在采集了多久、质量如何需要查询数据库，不能因为服务已部署就认定数据足够训练。无足够未见样本时先报告探索结果，不做可靠优势结论。

## 13. 分工与现有系统对接

用户负责输入数据格式、账户／执行、风险边界与服务器；队友负责策略假设、Agent／RL 研究和实验。队友可投入时间尚不确定，优先做一个能接入的最小策略，再按实际时间增加研究。分工正式决定仍由项目总览维护。

队友交付：资产范围、DataRequest、完整信号规则、回看／决策／持仓周期、目标数量计算、有效期、退出与失效规则、训练／验证分割，以及成本后结果。规则／ML／Agent 均输出既定 Decision，不直接签署订单。服务器风控需分别控制单资产、组合总敞口和挂单可能新增的敞口；收益过滤、资金预算与交易资格检查是不同职责。

当前正常执行链路已通过小额测试；StrategyContext 组装、Decision 执行器、无人值守风控和交易中断恢复仍待集成。做市接口需另行设计。详见[系统接口与部署](technical-plan.zh-CN.md)，数据口径见[数据来源与交易规则](data-development.zh-CN.md)。
